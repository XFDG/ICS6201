## 27届 AI Infra 秋招记录 02｜阿里星 AI Infra 一面，被一路追问到硬件细节

记录一次阿里星 AI Infra 一面。

这场没有上来写算法题，基本就是围绕简历一路往深处挖。面完最大的感觉是：**做过项目和真正把项目讲透，中间还隔着很远。**

面试官问得比较集中，核心都是一句话：你说你做过这个优化，那你到底知不知道它为什么有效？

### 1. H 卡到 B 卡迁移：不只要知道新特性名字

先聊到我最近在看的 H→B 迁移。

我提到了 TMA、Tensor Memory、Blackwell 上新的 Tensor Core 编程方式，以及一些新指令。但面试官很快把问题拉回工程：

- 这些硬件特性到底解决了什么瓶颈？
- 你实际准备怎么把它用到 Kernel 里？
- 原来的实现哪里慢？
- 改完以后性能收益来自哪里？
- 如果输入 shape 变了，这套方法还成立吗？

这一段我能讲概念，但真正落到“硬件资源—编程模型—Kernel 数据流—性能收益”这条链路时，明显不够扎实。

### 2. FlashAttention：为什么是 FA2，不是 FA3？

后面聊到 Attention 和融合。

面试官继续追：

- FA2 和 FA3 的核心差异是什么？
- Warp Specialization 为什么在 Hopper 上更重要？
- producer / consumer warp 到底分别干什么？
- TMA 在这里承担什么角色？
- 如果已经有 FA3，为什么你的场景还在用 FA2？
- Attention 后面接通信、O-Proj、RMSNorm、Router GEMM，哪些真的值得融合？

我当时更多是在讲“能融合什么”，但面试官明显更关心：

**为什么要融合，瓶颈在哪里，融合之后减少的是 launch、HBM traffic，还是通信等待？**

### 3. 多卡场景：TP、通信和融合不能拆开看

项目里涉及 TP 后，问题开始从单算子往系统层面走。

比如：

- TP 下为什么会出现额外的 All-Reduce？
- 通信能不能和计算 overlap？
- 如果把多个算子 fuse 到一起，会不会反而破坏通信调度？
- Kernel 变快以后，端到端为什么不一定同比例变快？
- 如果已经是 launch-bound，为什么不直接用 CUDA Graph？

我又顺着 CUDA Graph 讲到之前定位过的一次 TP + Graph 稳定性问题。

这部分能讲出真实排查过程，所以相对顺一点。

### 4. Deterministic：为什么算法同学这么在意？

面试官还追问了确定性计算。

我的回答核心是：GPU 并行规约时，浮点加法顺序变化会带来微小数值差异；对于算法基线、回归测试，以及一些对数值扰动敏感的 MoE / RL 场景，这种差异会影响可复现性。

继续往下就会问到：

- Split-K 为什么容易破坏确定性？
- 不切 K 为什么更容易保证固定累加顺序？
- 为了确定性牺牲性能以后，怎么把性能补回来？

这一块和我做过的 Router GEMM 优化比较贴，所以能接住。

### 5. 面试官给我的反馈，比题本身更有价值

最后我直接问面试官：我哪些地方还不够好？

他的反馈大意是：

**有实习经历以后，不能只停留在“我调用了什么、接了什么库、做了什么 feature”。要继续往下追硬件、编程模型、数据流、通信和真实瓶颈。**

尤其是做 Kernel / AI Infra，最好形成自己的判断：

- 什么时候是 compute-bound？
- 什么时候是 memory-bound？
- 什么时候其实是 launch-bound？
- 为什么这套实现适合这个 shape？
- 为什么多卡以后瓶颈会换地方？

这场面完以后，我重新意识到一个问题：

**简历上的每一个“优化”两个字，面试官都可以继续往下问五层。**

### 反问

我主要问了团队实际工作会更偏 Kernel、框架还是训练推理系统，以及我目前背景如果进组最需要补什么。

面试官给我的建议还是：底层基础再扎实一点，尤其是 GPU 架构和真实 Kernel 实现。

### 感受

这场不是题特别偏，而是问得非常“工程”。

会名词没什么用，真正要能把：

**现象 → 定位 → 瓶颈 → 方案 → 正确性 → 性能验证 → 端到端收益**

完整讲出来。

继续补课。

## 27届 AI Infra 秋招记录 03｜小米 AI 算子开发一面，从 CUDA Graph 问到 GEMM 和 Profiling

记录一次小米 AI 算子开发一面。

这场整体非常贴“算子开发”这个岗位，基本没有绕开简历，问题从 CUDA Graph、GEMM 一路问到 shared memory、profiling、Attention 和图优化。

### 1. CUDA Graph：不是会说 capture / replay 就够了

先问 CUDA Graph 是什么、为什么能加速。

我回答的是：把一系列 GPU kernel launch 和依赖关系捕获下来，后续直接 replay，降低 CPU launch overhead，比较适合执行路径和 shape 稳定的场景。

继续追问：

- Graph 怎么创建？
- capture 和 replay 分别发生什么？
- 哪些场景不适合 capture？
- shape、地址、控制流能不能变化？
- CPU/GPU 同步操作为什么会影响 capture？
- Graph 为什么在很多小算子的模型里更有价值？

这一段大方向能答，但一些 Graph 内部机制和我项目里的融合算子问题，当时有几处混在了一起。

面试完以后重新梳理了一遍：**CUDA Graph 本身解决的是 launch / submission overhead，算子融合解决的是另外一层问题，不能混着讲。**

### 2. Router GEMM：为什么 small-M 特别值得优化？

接着深挖我做过的确定性 Router GEMM。

原来的实现 config 比较固定，在 decode 的 small-M shape 下会浪费很多计算资源。

我做的思路是：

- 能用成熟高性能实现的优先走成熟实现；
- 不支持的精度 / shape 用自己的 Full-K 路径；
- K 维不切，M/N 做 tiling；
- 最后保留原始实现作为 fallback。

面试官继续问：

- 为什么不切 K 能保证更好的确定性？
- 性能提升到底来自哪里？
- 是减少 padding，还是提高 occupancy？
- 如果 shape 再小会怎样？
- 为什么不全部自己手写？

这部分因为确实做过，整体回答得比较顺。

### 3. 手写 GEMM，经典问题一个没少

然后开始问通用 GEMM 优化：

- global memory → shared memory → register 的数据流；
- block / warp / thread tiling；
- 为什么要做数据复用；
- shared memory bank conflict；
- padding / swizzle 怎么缓解 bank conflict；
- warp specialization 的意义；
- epilogue fusion 为什么可能有效。

属于比较标准的 GPU Kernel 基础，但真到面试现场，如果平时只看代码不自己画数据流，很容易讲散。

### 4. Nsight Systems 和 Nsight Compute 怎么分工？

面试官问到 profiling。

我的理解：

- Nsight Systems 更适合先看时间线、CPU/GPU overlap、kernel launch、通信和 bubble；
- Nsight Compute 再深入单个 kernel，看 memory throughput、SM 利用率、occupancy、stall reason、cache 等。

然后又问：你怎么判断 compute-bound / memory-bound？

这类问题最好别只背定义，而是结合真实 case：

如果 Tensor Core 没吃满、DRAM 已经接近上限，优化方向和“SM 很闲、kernel 很碎”完全不一样。

### 5. Attention / FlashAttention

后面也问了 MHA / Attention 的基本数据流：

QKV → QKᵀ → scale / mask → softmax → V。

FlashAttention 我能说出减少中间矩阵落 HBM、tiling、online softmax 这些大方向，但继续到更细的 kernel mapping 时，我当时就没有硬装，直接说自己深入做得不多。

### 6. 图优化和算子融合

还聊到了 graph level 的 fusion：

- 哪些节点可以融合？
- 依赖关系怎么判断？
- 融合后原节点怎么处理？
- 为什么 fusion 不一定总能带来收益？

我自己的理解是：融合不是越多越好。寄存器压力、共享内存、调度灵活性、并行度都有可能因为融合变差。

### 反问

我问了后续流程和团队具体做什么。

了解到后续还会有技术面，团队工作和自研芯片上的算子库、编译 / 算子优化比较相关。

### 感受

小米这场非常像一张“GPU 算子开发知识树”：

**CUDA Graph → GEMM → memory hierarchy → profiling → Attention → fusion。**

哪一块项目写到简历上，基本都会被继续往底下挖。

## 27届 AI Infra 秋招记录 04｜字节大模型推训优化一面，现场写 CUDA Row-Max

记录一次字节大模型推训优化一面。

这场给我的感觉是“项目深挖 + CUDA 基础 + 现场编码”，整体节奏很快。

### 1. 先从 Router Replay 开始

面试官先让我讲最近做的推训一致性项目。

我介绍了一个 MoE RL 场景下的 Router Replay：rollout 侧记录每个 token 在 MoE layer 里选择的专家，训练侧重算时复用路由结果，减少 rollout / training 之间因为数值差异产生的路由 mismatch。

继续问：

- 为什么 rollout 和 training 会选出不同专家？
- mismatch 对 RL 有什么影响？
- 记录的数据怎么从 rollout 传到 trainer？
- 规模上去以后额外数据会不会把通信放大？
- 怎么验证不是“看起来能跑”，而是真的稳定？

这类项目不能只讲最终指标，面试官更关心数据到底从哪来、经过谁、在哪里消费。

### 2. Deterministic Router GEMM

然后问到确定性计算。

重点还是：

- Split-K 为什么可能导致非确定性？
- Full-K 的代价是什么？
- small-M 下固定大 config 为什么浪费？
- 怎么做 dispatch / fallback？
- 单 kernel 快了以后，E2E 到底能提升多少？

这部分也是我秋招被反复问的一条主线。

### 3. TP + CUDA Graph hang 怎么定位？

接着问稳定性问题。

我讲了自己做控制变量的过程：

Graph off 正常 → Graph on 出问题；  
TP=1 正常 → TP>1 出问题；  
继续缩小到通信相关 fused kernel，再通过最小复现和社区实现去定位。

面试官比较在意的不是最后那一行修复，而是：

**你怎么从一个“大规模训练会卡死”的现象，一层层缩成一个算子级 bug？**

这个思路后来几场面试也一直被问。

### 4. 现场 CUDA：1000×1000，每行求最大值

代码题是一个很 GPU 的题：

给一个二维矩阵，对每一行求最大值。

我先给最基础版本，然后继续讨论怎么优化：

- 一个 block 负责一行；
- 每个 thread 处理多个元素；
- 先做 thread-local max；
- 再 shared memory reduction；
- 最后可以用 warp shuffle 继续减少同步开销。

面试官会继续看：

- memory access 是否 coalesced；
- block size 怎么选；
- shared memory 要多少；
- warp 内怎么规约；
- 如果列数不是 block size 整数倍怎么处理。

题本身不算特别难，但比单纯 LeetCode 更贴岗位。

### 反问

我问了后续流程和组里的方向。

大致是还会继续有技术面，工作会偏大模型推理 / 训练系统优化，以及多硬件后端上的性能工作。

### 感受

这场让我感觉字节比较看重一件事：

**你是不是能真的下到 kernel，也能抬头看系统。**

只会 CUDA 不够，只会框架也不够。

## 27届 AI Infra 秋招记录 05｜阿里云 MLSys 一面，Mooncake、Router Replay 和合并区间

记录一次阿里云基础软件 MLSys 一面。

这场和我提前了解到的方向很一致：Mooncake、KV Cache、RL 数据传输、推理框架。

开场面试官先介绍了团队，方向从底层系统一直做到上层 AI Infra，Mooncake 是比较重要的一条线，同时也会参与推理框架和训练 / rollout 数据传输。

### 1. 手写题：合并区间

上来先写了一道合并区间。

思路就是：

1. 按左端点排序；
2. 线性扫描；
3. 如果当前区间和上一个区间重叠，就更新右端点；
4. 否则开启新区间。

题本身不难，但现场 C++ 语法有点生，暴露出一个很现实的问题：

**AI Infra 面试再底层，手写代码也不能荒。**

### 2. Router Replay：从 8 卡追到多节点通信

项目部分重点问 Router Replay。

除了原理，还继续追：

- rollout 侧到底记录什么？
- 数据在什么时候从 GPU 搬出来？
- trainer 侧什么时候再搬回 GPU？
- 大规模以后为什么通信会突然变重？
- All-Gather / 跨节点传输的额外开销怎么控制？
- 为什么要压缩路由信息？

我也讲了从单节点验证扩到多节点以后，新增 metadata 会放大通信开销，所以不能只看“功能跑通”。

### 3. RL rollout 数据，到底该不该全量读？

这一段很有意思。

面试官问：训练节点消费 rollout 数据时，是把整份 rollout 都读过来再挑自己需要的，还是只按需读取？

我当时先按自己的直觉回答了全量读取，随后被指出：规模大以后，全量读会浪费带宽，很多系统更倾向于让完整数据留在存储端，consumer 只读自己真正需要的 slice。

这一问直接把话题从“做一个 feature”拉到了分布式数据系统。

### 4. NCCL / RDMA / GPU Direct Storage

后面继续问通信：

- NCCL 到底是什么层次的东西？
- NVLink 和 NCCL 是什么关系？
- RDMA 解决了什么问题？
- GPU 和 CPU、GPU 和远端内存、GPU 和 SSD 分别怎么传？
- GDS 是什么？

这里我明显有短板。

尤其是当时把“通信库”和“网络协议”混在一起讲了一部分，面完后专门重新补了 NCCL、RDMA、GPUDirect 这一整条链。

### 5. PD 分离和多级 KV Cache

因为团队做 Mooncake，KV Cache 自然问得很深：

- Prefill / Decode 为什么值得拆？
- PD 分离的收益到底来自延迟还是资源利用率？
- KV 从 GPU HBM、CPU DRAM、远端内存到 SSD，层级代价怎么变化？
- 什么情况下拉远端 KV 还不如重算？
- Prefix Cache 怎么复用？

这部分能讲大框架，但多级缓存和实际数据流当时还不够熟。

### 反问

我继续问了团队后续更可能做什么。

整体还是围绕 Mooncake、推理框架、KV Cache、数据传输和底层系统能力展开。

### 感受

这场和纯 Kernel 面非常不一样。

它更像是在问：

**如果把一台 GPU 的问题扩成 100 台机器，你原来的优化思路还成立吗？**

很多时候真正贵的已经不是那几微秒算子，而是数据到底放在哪、怎么传、谁来消费。

## 27届 AI Infra 秋招记录 06｜阿里云 MLSys 二面，数据结构、网络、NCCL 和 KV Cache 系统设计

继续记录阿里云 MLSys 二面。

和一面相比，这场更“系统”：前面先扫计算机基础，后面再深挖项目，最后直接聊到多节点 KV Cache 和 PD 分离怎么设计。

### 1. 数据结构基础

先问得很基础：

- 链表查找复杂度；
- 二叉搜索树最坏情况；
- Hash 和 Tree 怎么选；
- 如果做 timer / 定时任务队列，什么数据结构合适；
- heap 的插入和取最小值复杂度。

有几处复杂度我现场回答得不够干净。

这也提醒我：做 Infra，OS / 网络 / 数据结构这些基础是真躲不过。

### 2. TCP / UDP

然后问网络：

- TCP 和 UDP 区别；
- 三次握手；
- seq / ack；
- 同一台交换机上同时存在 TCP flow 和 UDP flow，会有什么区别。

题目看着是八股，但面试官其实在看你能不能把“可靠性、拥塞控制、延迟、吞吐”这些东西和系统场景联系起来。

### 3. TP + CUDA Graph hang

项目里还是重点问到之前那个 hang。

这次追得更细：

- 为什么 TP=1 不出问题？
- 为什么 Graph off 不出问题？
- fused communication kernel 里的 flag 在做什么？
- 为什么一个特殊浮点值会导致两卡互相等待？
- 怎么证明修复以后不是偶然好了？

这一段我回答得比之前成熟很多，因为已经被连续几场面试拷打过了。

### 4. Deterministic Router GEMM

继续问 Full-K、Split-K、DeepGEMM / Triton fallback。

最关键的问题还是：

**你的性能提升到底来自哪里？**

不是“我换了个库”，而是 small-M 下固定 config 有大量无效 tile / padding / 资源浪费，动态路径让实际工作量和 launch configuration 更匹配。

### 5. NCCL：Ring 和 Tree 怎么选？

面试官问 Ring All-Reduce 和 Tree All-Reduce。

我回答的核心：

- Ring 更容易把带宽吃满，适合大消息；
- Tree 通信步数更少、延迟更低，小消息或 latency-sensitive 场景可能更合适。

然后继续聊拓扑、节点内 / 节点间，以及为什么算法不是固定选一个。

### 6. 系统设计：Prefill 节点怎么把 KV 给 Decode 节点？

最后直接变成开放题。

如果做 PD 分离：

- KV 放哪？
- Prefill 节点算完以后怎么传？
- 什么时候走 RDMA？
- 小 KV 和大 KV 是否应该走同一条路径？
- 如果 decode 节点负载很高怎么办？
- 是 push 还是 pull？
- 怎么考虑缓存命中和调度？

我当时能给出“根据数据大小、负载和传输代价做动态选择”的框架，但细节不够成体系。

### 反问

我问了如果加入团队，最可能负责哪类工作。

面试官提到推理框架、Mooncake，以及更底层的 Kernel / mega-kernel 都可能涉及。

### 感受

这轮最大的感受：

**AI Infra 二面很容易从“一个算子怎么写”突然跨到“一个分布式系统怎么设计”。**

底层性能和系统设计不能只准备一边。

## 27届 AI Infra 秋招记录 07｜百度 AI Infra 一面，Router Replay、CUDA Graph 和推理框架被连续深挖

记录一次百度 AI Infra 一面。

面试官开场介绍，团队大致有三类工作：

- 推理性能优化；
- RL / rollout 相关 Infra 支撑；
- 训练侧的一些系统支持。

和我简历匹配度挺高，所以后面几乎全是项目深挖。

### 1. Router Replay：你到底改了哪一层？

我先讲 R3 / Router Replay。

面试官没有停在“记录 Top-K 然后训练时复用”这个结论，而是继续问：

- 路由信息具体从哪一层拿？
- 每个 token、layer、expert id 怎么组织？
- rollout 到 trainer 的完整链路是什么？
- CPU / GPU 之间什么时候发生搬运？
- 你自己真正负责了哪一部分？

这场对“ownership”问得很直接。

不能把整个项目都说成自己做的，必须明确哪些是原方案、哪些是团队已有链路、哪些是自己接入、验证和修改的。

### 2. 推理引擎结构

随后问：你对 vLLM 这类推理引擎到底了解多少？

我从请求进入开始往下讲：

API → Scheduler → Worker / Model Runner → Model → Operator / Kernel。

继续追：

- Scheduler 和 Model Runner 之间怎么传控制流、数据流？
- Prefill / Decode 怎么调度？
- KV Cache 怎么分配？
- MoE 下面什么时候发生通信？

这部分我能画出大的层级，但再往框架内部控制流走，就承认自己主要负责算子层，没有硬编。

### 3. CUDA Graph：Full 和 Piecewise 为什么要分？

后面继续问 CUDA Graph：

- Full Graph 和 Piecewise 的差异；
- 为什么 prefill / decode 的 graph 处理不同；
- Graph 的显存怎么管理；
- capture 后地址、shape、kernel launch 参数哪些能变；
- 哪些 host-device 操作会让 capture 失败。

这部分当时有些细节回答得不够严谨。

### 4. TP + CUDA Graph hang

自然又追到项目里的 hang：

Graph on + TP>1 才容易出现，最终缩到一个 fused communication kernel 的状态判断。

面试官继续问：

- 这个 kernel 为什么只在 Graph 路径出现？
- 到底改的是原始计算图还是 Graph replay 路径？
- 为什么是偶发，长时间运行后却几乎必现？
- flag 的位级比较为什么会误判？

这部分问得非常细。

### 5. Deterministic Router GEMM

继续聊：

- 为什么训练 / RL 需要 deterministic baseline；
- Split-K 和累加顺序；
- Full-K 怎么做；
- M/N tiling；
- fallback；
- 单算优化和 E2E 收益。

### 6. MHA / GQA / 量化基础

后面还扫了一些知识：

- MHA / GQA；
- AWQ；
- QAT；
- RL 框架和算法了解程度。

有些我确实没准备好，尤其是 GQA / QAT 当时回答得比较差，直接暴露知识盲区。

### 反问

我问了组里的具体工作和后续方向。

整体和开场一致：推理优化 + RL Infra 支撑，比较看重既能做算子、又能理解上层推理链路的人。

### 感受

这场最大的教训是：

**简历写“熟悉 vLLM / RL Infra”以后，面试官真的会按“熟悉”来问。**

以后对“了解、使用过、做过、熟悉”这几个词要更谨慎。

## 27届 AI Infra 秋招记录 08｜字节 AI Infra 二面，从 Router Replay 一路追到 2D Reduce

记录字节 AI Infra 二面。

如果说一面偏“项目 + CUDA”，二面明显更喜欢追问设计合理性。

不是问“你做了什么”，而是一直问：

**为什么这样做？有没有更简单的方案？**

### 1. Router Replay 的指标到底代表什么？

先重新讲 Router Replay。

面试官追着几个指标问：

- Router mismatch 为什么应该下降？
- KL 在这里反映什么？
- 你引用的论文指标到底怎么定义？
- Replay 做对以后，哪些指标是“必然会改善”，哪些才真正说明训练更稳定？

这一段我有一个论文指标解释得不够清楚，现场能明显感觉到自己只是“用过”，没有把定义彻底吃透。

### 2. 三元组为什么要做 Hash？

我讲到把 token / MoE layer / Top-K expert 信息做压缩。

面试官直接质疑：

既然 token、layer 本身都是连续维度，为什么非要做 Hash / KV？

能不能直接用连续 Tensor，根据下标访问？

这个问题我后来觉得问得特别好。

当时的实现更偏“先快速把东西做出来”，但从系统设计看，连续 buffer / tensor 确实可能更简单、额外 metadata 更少。

### 3. Router Replay 并没有解决所有不确定性

继续问 TP 下的 deterministic。

面试官指出：你 replay 的只是 routing decision，但 TP / reduction 自己仍然可能有数值不确定性。

这一点很关键。

**Router Replay 解决的是某一个来源的不一致，不等于整个训练链路 bitwise deterministic。**

### 4. Router GEMM：Full-K 到底在保证什么？

继续问：

- Split-K 为什么可能改变累加顺序？
- Full-K 为什么更容易 deterministic？
- DeepGEMM 只覆盖部分 dtype 怎么办？
- Triton fallback 如何选 config？
- small-M 的加速到底是不是来自减少无效计算？

这部分回答相对稳定。

### 5. 并行基础暴露短板

后面突然问 TP / EP / DP / PP。

我当时有些概念说混了，尤其是“哪一种并行对应哪一种通信”没有非常干净。

面完后重新画了一遍：

- DP：副本 + 梯度同步；
- TP：层内切分；
- PP：层间 pipeline；
- EP：专家切分 + token dispatch / combine。

基础概念越常见，越不能说错。

### 6. Coding：先问 GPU 2D Reduce，后换成数组原地位移

第一题是二维 Reduce。

面试官关注的不只是 shared memory reduction，而是：

- reduce 维度访存不连续怎么办；
- 某一维只有 64，parallelism 不够怎么办；
- 子问题怎么划分；
- 怎么提高 coalescing。

我当时回答得比较一般。

后面换成 CPU 题：数组原地循环位移，不允许额外空间。

最后想到“三次翻转”。

### 反问

问了后续流程和可能做的方向。

大致是 2–3 轮技术面再到 HR，岗位可能落在推理 / 训练框架和底层性能之间。

### 感受

二面最值得记住的一句话不是某道题，而是一个思维习惯：

**写出来不代表设计合理。**

面试官会继续问：有没有更简单的数据结构？有没有更低的存储成本？有没有少一次通信的方法？
