# OPPO 高性能计算与端侧部署

> 技术面复盘 · 多卡稳定性 / 确定性 / GPU 基础 / 端侧迁移。根据个人语音转写提炼，问题均已改写；公司与轮次沿用来源文件标注，不代表官方题库。

## 一、这一轮主要考什么

主线是把服务器端算子优化经历讲成可验证的工程过程，再判断这些能力能否迁移到资源受限的端侧设备。面试会连续追问根因、方案边界、已有社区方案和本人实际贡献。

## 二、源记录中可确认的提问

1. 多卡通信等待与浮点标志值有什么关系？为何考虑用位级判断？
2. 使用的是自研通信机制，还是开源库？问题属于通用缺陷，还是特定配置才触发？
3. 推理与训练的 Top-k 专家选择为什么可能不一致？“非确定性归约”具体指什么？
4. 问题影响有多大？已有通用方案为什么不能直接满足需求？
5. 新方案与原有确定性方案相比，付出了什么时间、空间或工程成本？
6. 修复是否获得上游确认？怎样区分内部修复、已提 issue 与已合入贡献？
7. 服务器 GPU 上的排障和性能经验，迁移到手机端时哪些仍然有效？
8. 将约 4B 规模的模型部署到手机端，需要优先考虑哪些资源约束？
9. 在成熟计算库与 AI 编程工具已存在的情况下，开发者如何体现算子优化价值？
10. 如何衡量空间换时间是否值得，怎样证明方案适合实际负载？
11. 介绍线程、warp、block、SM 与存储层次，解释 shared memory 的使用边界。
12. 什么是 shared memory bank conflict？你会怎样构造验证实验？

## 三、整理补充：回答准备提纲

### 稳定性案例用“证据链”组织

先画等待方和写入方，再写出状态何时变化、用什么类型存储、由谁读取。将“现场出现超时”与“根因已经定位”分开陈述。准备开关对照、卡数对照、最小复现和修复后回归四类材料，不依赖一句“改完没再挂”结束说明。

转写中的位宽、负零与 FTZ 描述有混用，不能照抄成标准解释。复习时应回到对应版本源码，明确载荷类型、比较类型与实际位模式；没有代码证据时，保留为待核对项。

### 从服务端迁移到端侧

可用一张预算表组织思路：权重和运行时内存、KV Cache 与临时张量、量化与精度、算子支持与回退、延迟、功耗和持续运行温度。分别列“已知约束”“需要查设备文档的约束”“准备实际测量的指标”。不要只用模型参数量判断能否部署。

### 算子优化的个人贡献

按“识别异常 → 构造复现 → 提出假设 → 改动实现 → 正确性与性能验证 → 交付回归”说明本人动作。AI 可以参与生成代码和分析报告，但需要能够解释关键分支、失败方案和最终取舍。

## 四、模拟追问与练习

- 如果异常只在某种数据分布中出现，如何避免复现输入遗漏关键条件？
- 如果某方案单算子更快，却多占显存，如何比较整机能容纳的并发请求数？
- 给一个陌生移动端加速器，先读哪些接口、算子和内存文档？
- 画出 block 内数据复用范围，并说明跨 block 协作准备使用哪种机制。

练习产出：一张通信状态图、一页端侧资源预算、一次有基线和误差检查的简化算子实验。

不要把共享内存表述成任意 block 都可直接共享；不要把社区已有方案说成本人原创；不要把一次特定环境的收益写成普遍加速结论。基础概念校准见本目录《阅读说明与基础校准》。
