# 小马智行三面：性能证据与工程闭环

> 技术深挖复盘 · 并行度 / 输入分布 / 正确性验证 / 偶发故障。源记录问题已改写，公司与轮次沿用文件标注，不代表官方题库。

## 一、这一轮主要考什么

这一轮不断将抽象描述压到可核实的事实：到底切了哪一维、为什么选这个阈值、实际走哪条后端、数据从哪里来、收益覆盖多少任务。仅记结论和术语很难应对连续追问。

## 二、源记录中可确认的提问

1. 训练反向算子的原始调度具体如何阻塞并行？改动了哪些逻辑？
2. 分块数量如何选择？给定输入时实际会开多少并行工作？
3. 为什么采用某个切分阈值？有实验依据，还是仅便于理解？
4. 怎样判断并行度足够，而不是只观察一个 SM 利用率数字？
5. 测试数据来自真实输入、dump 还是构造？它们各有哪些限制？
6. 如何解释“同样数据、不同 shape”？测试维度是否定义清楚？
7. 单算子、单层、整模型收益分别如何测量和统计？
8. 多后端与 fallback 各解决什么问题？真实请求分别走哪条路径？
9. 新 Kernel 的切分与调度怎样分别解决 padding 和确定性问题？
10. 开发阶段怎样保证正确？如何与发版前的整网评测衔接？
11. 能否复用一套通用正确性测试，而非每个算子重新写一套？
12. 偶发 hang 为什么归因到某条路径？如何逐步缩小实验范围？
13. 修复的影响面怎样量化，除了“没有再次失败”还能提供什么？
14. AI 写出的代码，开发者是否理解其组织方式和方案取舍？

## 三、整理补充：准备四份证据

### 证据一：输入与执行路径表

逐项记录 shape、dtype、layout、硬件、版本、开关、选中后端和 fallback 原因。说明阈值来自什么测试；对没有测过的输入明确留白。不要用一种 shape 的结果概括所有负载。

### 证据二：正确性矩阵

明确比较对象与误差标准，区分数学定义、容差一致、同实现重复运行一致和跨实现逐位一致。列出随机、极值、边界尺寸和不同布局的测试。原记录中的“都是确定性所以应该 bitwise”不能直接作为正确性证明。

### 证据三：性能统计与消融

每个改动独立记录基线、样本数、预热、计时范围和统计量，再记录组合效果。整网收益与单算子收益分别计算；还需要核对目标算子在总时长中所占比例，以及优化是否改变了其他部分。

### 证据四：故障影响与回归

列出触发条件、复现概率、任务损失、修复覆盖的版本与配置、仍未覆盖的情况。使用对照实验区分“同一症状”与“同一根因”。线上影响、内部监控和团队细节不应复制进公开面经，可用脱敏结构说明方法。

## 四、面试前的模拟检查

- 用一张图解释矩阵切分，标出实际代码中的循环和归约维度。
- 任选一个性能数字，回查它对应的实验和原始单位。
- 任选一条后端路径，说明触发条件、失败方式和回归用例。
- 对一个失败方案说明为什么没选它，避免只说“试过，效果不好”。
