## 27届 AI Infra 秋招记录 09｜MiniMax AI Infra 一面，项目被追到“你这个 Hash 设计是不是多余了”

记录 MiniMax AI Infra 一面。

这场整体很技术，项目深挖的风格不是“复述一遍”，而是会现场和你一起重新设计。

### 1. 先聊 H→B 和 FlashAttention

开头聊到不同硬件平台和我最近在看的 B 卡。

我提到 FA2 → FA3 的 Warp Specialization、TMA，以及 Blackwell 上新的 Tensor Core / Tensor Memory 编程方式。

面试官重点还是问：

- 硬件升级以后瓶颈怎么变化？
- 数据搬运变快以后，Softmax / elementwise 会不会反而成为新瓶颈？
- Kernel 应该怎么跟硬件一起演化？

属于比较开放的交流。

### 2. CUDA Graph + TP hang

然后深挖稳定性问题。

我从控制变量讲：

- Graph off 正常；
- TP=1 正常；
- fused communication path 关掉正常；
- 最后定位到状态位 / sentinel 判断。

面试官继续问 flag 为什么这么设计、dtype 改变为什么会触发误判、为什么长轮次更容易复现。

### 3. Router Replay：Hash Table 真的是最优设计吗？

这一段是全场我印象最深的。

我讲到把 token / layer / expert 信息编码，方便存储和 replay。

面试官直接问：

**为什么要 Hash Table？**

token、layer 都是连续下标的话，完全可以用连续 Tensor / Buffer，甚至直接压成二维或三维数组。

这样：

- 不用额外存 key；
- 访问逻辑更简单；
- 显存更省；
- locality 也可能更好。

我当时直接承认：最初为了快速落地，没有把数据结构设计想得这么完整。

这反而让我觉得这场很有价值。

### 4. Deterministic Router GEMM

继续问：

- bf16 / fp16 / fp32 怎么覆盖；
- Split-K 为什么会影响 deterministic；
- Full-K 是不是本质上就是关掉 Split-K；
- config 怎么根据 token / shape 选；
- 为什么小 shape 提升明显；
- fallback 怎么保证功能完整。

基本就是项目最核心的实现逻辑。

### 5. TP / EP / DP / PP

也扫了模型并行。

我这部分回答并不漂亮，有些通信模式说混了。

又一次提醒自己：

**做 MoE 算子，不能只会 MoE Kernel，不知道 token 在卡之间怎么走。**

### 6. Coding：2D Reduce + 数组原地 Rotate

先给了一个 GPU 二维 reduce，关注：

- reduce 维度的 coalescing；
- 维度较小时并行度；
- block / warp 怎么划分。

我一开始更多在讲 shared memory / warp reduce 技巧，但面试官其实更想听整个问题的 partition。

后来换了一道 CPU 原地数组位移，最终想到三次 reverse。

### 反问

我问了团队更偏训练还是推理，以及多模态模型训练和纯文本模型在系统上有什么不同。

交流到 Attention mask、数据形态和模型结构这些差异。

### 感受

MiniMax 这场让我明显感觉：

**项目深挖的最高一层，不是问你代码怎么写，而是面试官重新站在设计者角度问：如果今天重做，你还会这么设计吗？**

## 27届 AI Infra 秋招记录 10｜曦望 AI 训推优化一面，国产推理卡到底需要什么样的算子工程师

记录一次曦望 AI 训推优化一面。

这场和互联网大厂的感觉很不一样，因为对方本身做推理芯片，所以问题天然会把模型、算子和硬件绑在一起。

### 1. 为什么集成电路专业最后在做 AI Infra？

开场先聊背景。

面试官注意到我是集成电路专业，但实习基本都在算子、推理和 RL，所以先问课程和方向怎么衔接。

我解释了自己的路线：

硬件背景 → GPU / 加速器 → 算子 → 大模型训推系统。

这反而是一个比较自然的故事。

### 2. 推理卡为什么不一定需要完整训练算子？

面试官给了一个场景：

如果 H 卡负责训练，国产卡主要负责 rollout / inference，那国产推理卡是不是不一定需要完整训练反向算子？

答案是的。

这也引出了异构 RL：

- 一边训练；
- 一边 rollout；
- 中间做权重同步；
- 两边最关键的是训推一致性、吞吐和数据传输。

### 3. Router Replay：推理选的专家就一定“更对”吗？

聊到 R3 后，面试官问了一个我之前没从这个角度想的问题：

**你把 rollout 的 Top-K expert replay 给训练侧，隐含前提是什么？推理选出来的专家一定更好吗？**

其实 Router Replay 的目的不是证明 rollout 的专家“更优”，而是把两边 routing decision 对齐，减少同一策略下因为算子 / 数值路径不同带来的偏差。

这个区别很重要。

### 4. 路由数据怎么压缩、怎么容错？

继续问：

- token / layer / expert id 怎么编码；
- 为什么能减少通信；
- 是否有纠错机制；
- 数据传坏怎么办；
- 这套编码是不是只适配某一种模型结构。

我当时也承认，做的是更偏业务 / 模型特化的工程方案，不是一个完全通用的 codec。

### 5. RL Infra 到底看什么指标？

面试官反过来向我请教 RL Infra 平时重点看什么。

我总结了几个：

- reward 趋势和方差；
- KL；
- policy ratio / clipping 相关指标；
- rollout / train step time；
- 系统异常、通信、坏卡和算子错误。

如果指标异常，不一定就是算法本身，也可能是：

通信、配置、硬件、数据、算子，甚至某个节点状态异常。

### 6. 怎么最小化复现一个大规模 hang？

这场又详细聊了 TP + CUDA Graph hang。

面试官很关注：

一个几百卡、跑很多 step 才出问题的任务，怎么一步步缩成一个两卡甚至算子级复现？

我的思路还是：

版本回退 → 缩规模 → 改并行配置 → Graph on/off → TP=1/>1 → 关激进优化 → 锁定 fused communication kernel。

这类系统 debugging 的故事，其实比单纯“我修了一个 bug”更能展示能力。

### 7. 国产卡和 CUDA 生态差在哪？

因为我之前也做过国产 GPU 适配，后面聊到：

- API 层可能看起来很像；
- 真正差距往往在高性能库、编译器、算子覆盖度和长期 tuning；
- “能跑”距离“性能好”还很远。

对方团队本身也很关注算子库，这部分交流比较契合。

### 反问

我问了芯片当前定位、未来算子团队的工作，以及训练 / RL 支持会做到什么程度。

整体还是以推理为主，但会补训练 / rollout 所需能力。

### 感受

芯片公司的算子岗和互联网 AI Infra 最大区别之一：

**你做的不是在一个成熟 GPU 上再快 10%，而是要一起把硬件能力、runtime、算子库和模型真正拼成一个可用的软件栈。**

## 27届 AI Infra 秋招记录 11｜阿里 AI Infra 一面，确定性 Attention、FlashAttention、KV Cache 连环追问

记录一次阿里 AI Infra 一面。

这场前半段几乎围绕我最近刚做完的一个 deterministic Attention backward 优化，后半段转到 FlashAttention、FlashInfer、vLLM 和 KV Cache。

整体问得很连贯。

### 1. 最近做了什么？直接讲最新的

开场让我选一个最近最有代表性的工作。

我讲了一个 Sliding Window Attention backward 的性能问题：

在确定性 DQ 累加路径下，原实现为了固定累加顺序，cluster 大量排队，导致 backward 明显慢于 forward。

我的排查路径是：

- 先从 Nsight / trace 找到慢点；
- 确认主要耗时在 deterministic DQ；
- 分析 flag / cluster 的串行等待；
- 再尝试缩小参与范围、调整累加顺序和提高并行度。

### 2. 确定性不等于必须和旧 baseline bitwise 一样

面试官问：

改了累加顺序以后，怎么验证 correctness？

这里一个很关键的区分是：

目标是让**同一新实现多次运行能够稳定复现**，同时和参考实现数值误差在允许范围内；并不要求新旧两个不同累加顺序的实现 bitwise 完全一致。

继续追：

- 为什么 reverse order 会更快？
- 是 cache locality 还是并行度？
- tile 重排以后怎么保持确定性？

这一段问得比较深入。

### 3. FlashAttention 最初到底解决什么？

接下来直接问 FA。

不是问 FA2 / FA3 feature，而是回到最基础的一问：

**FlashAttention 最初为什么存在？**

我先说 tiling、数据复用、producer-consumer，面试官一直把我往最核心的问题拉：

传统 Attention 会产生 QKᵀ、softmax 等大中间矩阵，频繁写回 / 读取 HBM；FlashAttention 通过 IO-aware tiling、融合和 online softmax，减少 HBM traffic。

然后继续追：

**softmax 需要整行信息，分块以后怎么计算？**

这就必须讲 online softmax / running max / normalization，而不只是“做 tiling”。

### 4. FlashInfer 和 FlashAttention 有什么区别？

因为简历写过 FlashInfer，继续被问：

- FlashInfer 是什么定位？
- 和 FlashAttention 有什么差异？
- 为什么推理场景会用它？

这部分我当时答得一般，只能讲自己真正接触过的 fused kernel，没有把整个库的定位讲完整。

### 5. vLLM / PagedAttention / KV Cache

后面转向推理：

- 为什么要 PagedAttention？
- KV Cache 为什么按 page 管理？
- full attention 下分页还有没有意义？
- prefix cache 怎么命中？
- 两个请求如何识别公共前缀？
- block hash 怎么组织？
- 新请求怎么和已有 block 做匹配？

面试官一路从“KV Cache 是什么”问到“如果让你自己设计 hash key，你怎么避免顺序冲突”。

很像现场系统设计。

### 6. 离线推理和在线 Serving 的优化目标不同

反问时聊到团队业务。

一个很有意思的点是：

在线 serving 更关心单请求 TTFT / latency；  
离线大批量推理可能根本不在意某条请求 100ms 还是几秒，更关心**整个数据集多久跑完、卡利用率和总吞吐**。

所以同样叫“推理优化”，目标函数完全可能不同。

### 反问

我问了团队所谓“推理引擎 / 平台”到底做什么。

对方介绍的更像一套面向大规模离线推理的垂直系统：底层推理框架、模型适配、资源利用率、任务容错和大数据处理结合在一起。

### 感受

这场最大的收获是：

**越往后面试，越容易被追到一个技术最初的原理。**

你会 FA4 新特性，不代表你就能回答“FA1 为什么要发明”。

基础原理还是得补。

## 27届 AI Infra 秋招记录 12｜字节 AI Infra 三面，主管面更像在判断“你到底是不是做系统的人”

记录字节 AI Infra 三面。

这场没有常规算法题，更多是主管视角的项目深挖和技术路线交流。

比起前两面，问题更关注：

- 你真正做了什么；
- 你的技术判断从哪里来；
- 如果把工作交给你，能不能独立把问题闭环。

### 1. 先聊真实工作边界

开场先花了不少时间确认我在当前团队里的定位：

- 团队整体在做什么；
- 我负责的是算子、通信还是框架；
- 哪些是其他小组负责；
- 项目最后交付给谁；
- 国产 GPU 那段经历主要做了哪些类型的算子和 benchmark。

这类问题其实是在确认简历里的 ownership。

### 2. TP + CUDA Graph hang，又被从头问了一遍

三面再次问到这个项目，但视角变了。

重点变成：

- 你怎么知道是通信问题？
- fused All-Reduce / Norm 里 flag 为什么这么设计？
- 为什么用浮点 sentinel？
- 为什么 dtype / 位级判断会导致互相等待？
- 修完以后怎么做 graph on/off 和多卡验证？

面试官还会直接指出：“这个问题本身不算特别复杂，关键看你有没有把底层设计逻辑搞懂。”

### 3. 为什么现在更多写 Triton / CuTe，而不是纯 CUDA？

我提到最近团队里更多用 Triton / CuTe DSL。

面试官追问原因。

我的回答主要是：

- 开发和迭代更快；
- 可读性更好；
- 更方便和算法同学 co-design；
- 很多模型早期瓶颈还没到必须手搓 CUDA 的程度；
- 先用更高层 DSL 把 layout / schedule 做对，收益已经很大。

这也是现在很多算子团队真实的开发取舍。

### 4. Router Replay：从 RL 流程一直问到 MoE 数据流

继续聊推训一致性。

面试官先让我从完整 RL loop 讲：

rollout → reward → old/new logprob → loss → backward/update → weight sync。

再问 Router Replay 插在哪一步。

然后突然问：

**一个 token 进入 MoE layer 后，完整 forward 数据流是什么？**

这一问我答得不好。

因为平时更多是对着具体代码和算子排查，并没有把整个 MoE block 的结构背得很熟。

这是三面很明显的扣分点之一。

### 5. 最新训练 Kernel：deterministic DQ

我又主动讲了最近的 Sliding Window Attention backward 优化。

这部分面试官会继续确认：

- 原来为什么串行；
- 多 SM 并行以后如何保持固定累加顺序；
- 全局 flag 改局部 flag 的收益；
- reverse order 为什么可能改善 cache；
- 多条链并行是不是改变了数值顺序。

这部分因为刚做完，回答明显比旧项目更扎实。

### 6. 国产 GPU：别只凭印象说硬件规格

后面聊到之前使用过的国产 GPU。

我按印象说了一些 cache / bandwidth / 对标卡的信息，面试官明确提醒其中有些点可能不准确，让我回去重新查 spec。

这个提醒很重要：

**硬件参数属于事实题，不能凭模糊记忆。**

### 7. 通信会成为下一阶段重点

最后面试官给我的反馈大意是：

项目做得比较实，但如果继续往算子 / AI Infra 深走，GPU 架构细节和通信都要继续补。

尤其是以后算子越来越快，通算融合、跨卡通信会越来越重要。

### 反问

我问了团队核心工作。

了解到团队目标偏向把云上的 GPU 训练 / 推理服务真正做出性能，让不同模型和客户 workload 在集群上跑得更好。

因此不是单纯“写 Kernel”，而是会把：

**GPU 性能 + 开源模型 + 推理训练框架 + 集群**

放在一起看。

### 感受

三面最大的感受是：

前两面可能在验证“你会不会”，主管面更像是在判断：

**你是不是一个能独立定位问题、知道边界、愿意继续往深处挖的工程师。**

技术知识不会可以补，但项目不能只剩一串漂亮数字。
