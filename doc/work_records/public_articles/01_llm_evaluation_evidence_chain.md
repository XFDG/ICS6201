# 从“跑完”到“可信”：LLM 推理优化评测的四层证据链

> 本文抽象自真实工程实践，涉及的环境、模型、平台、规模和实验数据均已匿名化。文中的示例只用于说明方法，不对应任何特定组织或线上系统。

## 结论先行

一次 LLM 推理优化实验显示“Workflow Completed”，最多只能证明编排系统走到了结束状态。要让结果真正可信，还需要同时建立四层证据：

1. **实验身份与控制变量可信**：明确到底运行了哪份代码、哪份运行产物、哪组开关和哪套评测器，并保证对照组只改变目标变量。
2. **执行过程与产物完整**：不仅服务要启动，预期任务、样本和结果文件也必须全部落盘，失败链路还要能定位到具体层级。
3. **正确性结论分层**：能力分数稳定、逐题预测一致、张量数值等价是三种不同强度的结论，不能互相替代。
4. **性能结果可重复且可归因**：单次端到端耗时只是一个观测值；稳定收益需要重复测量、负载匹配和分层指标。

这四层缺一不可。前一层没有建立，后一层即使出现漂亮数字，也很难解释。

## 一、第一层：先固定实验身份，再谈对照

推理实验最容易被忽略的问题，是“看起来配置一样”和“实际上运行同一环境”并不是一回事。源码版本只是输入，真正执行的是由源码、Python 依赖、CUDA 运行时、编译扩展和启动配置共同组成的运行产物。因此，一份合格的实验记录至少需要包含：

| 身份维度 | 应记录内容 |
|---|---|
| 运行产物 | 不可变镜像摘要或等价的制品 ID |
| 模型 | 匿名模型 ID、权重版本、精度和上下文上限 |
| 推理配置 | TP/DP/PP、显存预算、最大长度、批处理与图模式 |
| 优化开关 | 后端、环境变量、编译选项及实际命中日志 |
| 评测器 | 评测代码版本、数据版本、prompt、few-shot、答案抽取规则 |
| 请求口径 | 接口类型、并发、超时、重试、生成参数 |
| 资源环境 | GPU 类型、卡数、驱动和运行时版本 |

尤其要避免用可覆盖的镜像标签、浮动分支或“最后一次提交”充当实验身份。标签方便人阅读，不适合作为不可变证据；评测器也应固定版本，否则对照组可能在不知情的情况下使用了不同的数据处理逻辑。

### 两项优化应使用 2×2 正交对照

假设要同时验证优化 A 和优化 B，最小完备设计不是“旧版本对新版本”，而是下面四组：

| 组别 | 优化 A | 优化 B | 能回答的问题 |
|---|---:|---:|---|
| Baseline | 关 | 关 | 参考基线 |
| A Only | 开 | 关 | A 的独立影响 |
| B Only | 关 | 开 | B 的独立影响 |
| A + B | 开 | 开 | 叠加效果及交互影响 |

四组最好使用同一运行产物，通过显式开关选择路径。这样可以把依赖环境、编译器和基础代码差异从对照中排除。如果必须使用多个制品，也要证明它们来自同一构建基线，并记录每个制品的完整 manifest。

除目标开关外，其余变量应保持一致：模型、硬件、并行度、请求集合、并发、超时、缓存策略、随机性、评测器版本都不能只在某一组中调整。某个优化组 OOM 后单独降低并发，虽然可能让任务跑完，却已经失去横向可比性；正确做法是统一调整所有组并重新执行。

## 二、第二层：Completed 不等于完整

一个完整的评测链路通常包含编排器、推理服务、模型加载、健康检查、请求客户端、Evaluator 和结果汇总。Workflow 显示完成，只是其中一个状态机的最终状态，不能替代产物审计。

至少应核对以下内容：

- 预期的子任务是否全部被提交，而不是只看任务组名称。
- 每个任务是否都有结果文件、样本文件和最终指标。
- 样本数、任务数与评测定义是否一致。
- 运行记录是否保存了实际后端和开关，而不是靠提交顺序猜测。
- 汇总文件能否反向定位到输入样本与运行配置。

最稳妥的做法是为每次运行生成一份 manifest，记录“预期任务集合、实际任务集合、每个文件的哈希、样本计数和配置摘要”。只有预期集合与实际集合完全相等，才能把该运行标记为完整。

### Readiness timeout 只是外层症状

服务未就绪时，排查应沿启动链路逐层向内推进：

```text
调度与拉取制品
  -> 进程启动与参数解析
  -> 推理引擎初始化
  -> 模型加载与编译
  -> 健康检查
  -> 请求处理
  -> Evaluator 判分与回传
```

如果进程在参数解析阶段就退出，外层最终仍可能只显示 readiness timeout。此时没有任何 kernel 被执行，不能把故障归因于 CUDA、通信库或自定义算子。

一个常见陷阱是把带注释的文本粘贴进平台参数栏。例如：

```text
# experiment A --backend optimized --max-model-len 8192
```

`#` 只有在命令经过 shell 解释且启用注释语义时才表示注释。许多平台会把输入解析成结构化 argv，再直接传给进程；此时 `#` 和后面的说明都是普通参数，参数解析器会据此报错。公开或自动化的配置界面应使用独立字段保存说明，参数栏只接受可执行参数，并在提交前展示最终 argv 做 dry-run 校验。

当推理服务持续健康、请求已经排空，而某个评测任务仍然失败时，故障域应转向 Evaluator、Controller、单请求超时、Pod 生命周期或状态回传链路。没有日志时，可以收敛故障边界，但不能虚构一个精确根因。

## 三、第三层：正确性要分能力、逐题和张量三层

推理优化常见的误判是：聚合分数几乎不变，于是宣布“数值正确”。这实际上混合了三种不同口径。

| 正确性层次 | 典型证据 | 能支持的结论 |
|---|---|---|
| 能力回归 | Accuracy、pass@k、EM、任务级得分 | 没有观察到明显能力下降 |
| 逐题一致性 | 预测一致率、翻转方向、候选分数 | 相同样本的决策是否保持稳定 |
| 张量等价 | 算子输出、hidden state、logits、loss | 优化实现是否满足数值容差 |

聚合分数只统计最终答对多少题。如果一些样本从对变错，另一些从错变对，净变化可能接近零，但模型行为已经发生明显改变。因此，对照分析应先用稳定的样本键对齐两组结果，再统计：

- 预测完全一致的比例；
- “对变错”“错变对”和“错变另一个错”的数量；
- 配对样本上的显著性检验，例如 McNemar 检验；
- 每个候选 score 或 logprob 的差值；
- baseline 的 top1-top2 margin。

如果翻转主要集中在低 margin 样本，说明微小数值扰动跨过了决策边界；这有助于解释现象，但并不自动代表实现正确。对于目标是等价替换的算子，还应使用固定输入逐层比较：先比较算子输出，再比较每层 hidden state、最终 logits 和 loss，找到首个超过容差的位置。

反过来，逐题完全一致也不能证明某项优化有性能价值。某些短上下文、多选候选打分任务对 prefill 较重，却几乎不覆盖长上下文 decode；它可以证明能力未变，却可能完全错过优化最擅长的负载。

## 四、第四层：性能必须可重复，也必须匹配负载

端到端评测时间通常混合了制品拉取、模型加载、图编译、Evaluator CPU 开销、网络等待、集群调度和实际推理。把两次单独运行的总时长相除，不能直接得出 kernel 加速比。

可靠的性能实验至少要做到：

1. 区分冷启动和稳态，预热后再进入计时窗口。
2. 在相同资源池上交错执行各组，降低时段负载带来的偏差。
3. 每组重复多次，报告中位数、分位数和离散程度，而非只报最好一次。
4. 固定输入 token、输出 token、并发与批处理分布。
5. 同时记录端到端吞吐、TTFT、TPOT、请求延迟以及目标 kernel 指标。
6. 验证优化路径实际命中，并记录 fallback 比例。
7. 为 attention、MoE、通信等不同优化设计对应的专项负载。

能力 benchmark、服务压测和算子 microbenchmark 各自回答不同问题。最有说服力的报告不是选择其中一个，而是把三者串成证据链：microbenchmark 解释局部上限，服务压测验证系统收益，能力评测确认没有不可接受的回归。

## 五、发布前检查表

### 实验身份与控制变量

- [ ] 四组运行产物和评测器版本均可追踪、不可变。
- [ ] 2×2 对照只改变目标优化开关。
- [ ] 模型、硬件、并行度、请求和评测参数完全一致。
- [ ] 运行日志能证明实际命中的后端与开关。

### 执行与产物

- [ ] 预期任务集合等于实际提交集合。
- [ ] 每个任务都有完整结果，样本计数符合定义。
- [ ] 结果 manifest 保存配置、文件哈希和运行身份。
- [ ] timeout 已定位到具体层级，没有把外层症状当根因。

### 正确性

- [ ] 已区分能力回归、逐题一致性和张量等价。
- [ ] 已检查翻转方向、候选分数与决策 margin。
- [ ] 等价替换型算子已完成固定输入的逐层数值比较。

### 性能

- [ ] 已区分冷启动、稳态、服务级和 kernel 级时间。
- [ ] 每组重复运行，并报告统计分布。
- [ ] 专项负载确实覆盖优化的目标场景。
- [ ] 性能收益与正确性结论分别表述，边界清晰。

## 结语

LLM 推理评测的难点不在于“多跑几个 benchmark”，而在于让每个结论都能回答三个问题：运行的到底是什么、证据是否完整、差异能否归因。建立四层证据链后，“跑完”只是起点；只有实验身份、产物完整性、分层正确性和可重复性能同时闭环，结果才真正值得用于工程决策。
