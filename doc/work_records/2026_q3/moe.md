# MoE 架构与评测：公开工作记录

## 工作目标

围绕稀疏专家模型，完成了从架构澄清、feature-gated 实现、正确性验证到层级/端到端性能评估的工作拆解。核心原则是先确认语义与数据布局，再评估性能；“代码能跑”或单次吞吐变化不足以说明优化有效。

## 架构判断

对 latent/共享专家等实现路线，分别澄清了以下边界：是否改变训练目标、对权重存储和激活显存的影响、通信模块是否需要配套修改，以及推理侧改动能否在不重训的条件下验证。结论是：推理实现可以先做兼容路径和受控评测，但训练质量与最终架构等价性必须由模型侧定义并另行验收。

## 实现与正确性方法

- 用 feature gate 保留原路径，确保可随时回退并支持 A/B 对照。
- 建立语义 oracle，比较路由选择、专家输出、聚合结果和最终 logits，而非只比较是否完成请求。
- 覆盖单卡、张量并行及边界 shape；记录容差、精度、随机性处理和失败案例。
- 在性能测试前确认开关真正传入执行路径，避免“测试了错误配置”。

## 性能评测方法

层级 microbenchmark 与端到端 serving 分开进行。前者用于定位路由、dispatch、GEMM、通信等局部瓶颈；后者覆盖请求调度、缓存和系统开销。测试矩阵按 batch、上下文长度、生成长度和并行度分层，报告相对基线的趋势而非单个绝对数字。

阶段性观察显示，某些实现即使语义通过，也可能因额外重排、同步、通信或未命中优势 shape 而变慢。因此性能结论必须同时回答“在哪些条件下”“相对于哪个基线”“瓶颈在哪里”。

## 评测设计经验

1. 先冻结 baseline 和输入分布，再增加候选实现。
2. 单项优化和组合优化分开测，组合结果重新校验数值。
3. 将 profile 结果用于解释趋势，不把 profile 截图当作结论本身。
4. 对异常负收益先排查开关、构建产物、配置正交性和统计稳定性。
5. 对未获得加速的方案给出停止条件，避免持续消耗资源。

## 当前公开边界

本文不包含专有模型名称、权重、训练数据、内部实现位置、集群拓扑、运行记录或绝对业务指标。保留的结论仅适用于已验证的实验条件；训练质量、规模化收益和生产可用性仍需在授权环境中完成后续验收。
