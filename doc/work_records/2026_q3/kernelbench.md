# KernelBench 与算子接入：公开工作记录

## 结论先行

完成了 GPU kernel 生成/评测基准的调研、运行链路梳理、初步验证和模型候选对比。该类平台适合衡量“给定任务上的代码生成与性能优化能力”，但不能独立代表真实业务吞吐或工程成熟度。实际落地前应先修复评测链路问题，并以小规模 pilot 验证成本、稳定性和指标可信度。

## 平台方法

基准将任务描述、参考实现、候选 kernel、编译执行、正确性校验和性能测量串成闭环。可复用的工作方法包括：

- 将任务按计算/访存模式和难度分层，避免只看总分；
- 区分生成失败、编译失败、数值失败和性能失败；
- 对通过正确性的候选再进行性能比较，并标注统计口径；
- 对可修复的失败记录修复前后差异，形成工程迭代证据；
- 将模型输出、测试配置和结果摘要结构化保存，支持复查。

## 关键工程发现

评测链路自身的依赖版本、超时、缓存、资源隔离和失败归类会显著影响结论。任何大规模跑分前，应先用少量代表任务完成环境自检、正确性 smoke、性能 smoke 与结果落盘校验。候选模型对比也应把覆盖率、正确率、可编译率和正确候选的性能分开报告。

## 算子接入前置检查

另完成了算子接入评测系统的设计梳理。建议采用以下门禁：

1. 明确输入/输出语义、精度和容差；
2. 准备基线实现与可重复的最小样本；
3. 增加 shape、stride、边界长度和并行配置覆盖；
4. 记录性能指标、预热、重复次数和统计方法；
5. 将失败样本和回退路径作为交付的一部分。

## 后续建议

先进行小型 pilot：固定少量任务、候选模型和设备配置，验证评测成本与稳定性；通过后再扩展任务池。对任何“性能更好”的候选，均需有数值正确性、可重复测量和 profile 归因三类证据。
