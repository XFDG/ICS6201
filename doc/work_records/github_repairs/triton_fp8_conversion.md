# Triton FP8 转换：从编译断言到明确的接口错误

开发记录：2026-10-14 至 10-15。公开入口：[issue #12259](https://github.com/triton-lang/triton/issues/12259)、[PR #12290](https://github.com/triton-lang/triton/pull/12290)。

## 1. 现象与最终选择

E4M3 与 E5M2 直接转换未指定舍入模式时，NVIDIA 下沉路径发生断言。最终修订选择在前端清晰拒绝不支持的直接转换，保留用户显式写出的 FP16 中转链和同格式转换。最初自动插入 FP16 的方案已被维护者要求撤回，不能继续把它描述成最终实现。

## 2. 定位：相同位宽不等于无需舍入

原前端默认舍入逻辑主要依据目标 primitive 位宽是否减小。两种 FP8 都占 8 bit，但指数和尾数分配不同，因此同位宽转换仍可能需要舍入。

第一次只补 RTNE 后，错误变为“不支持该格式对的转换”。这暴露出第二层限制：给出舍入模式不能凭空补齐后端转换实现。将两个错误分开，避免只修第一个断言就宣布问题解决。

涉及位置为 `python/triton/language/semantic.py`，回归加入已有 `python/test/unit/language/test_core.py`。

## 3. 第一版：隐式 FP16 中转

有限 FP8 值可以精确扩展到 FP16，再走已有 FP16 到 FP8 的舍入路径。第一版据此避免直接下沉到缺失转换。

原版与修复版共享同一份、匹配源码的原生编译库，只改变 Python 前端和新增测试，减少编译环境差异。测试曾因 masked load 使用整数填充值而在目标转换之前失败；改为浮点填充值后才进入有效的转换验证。

第一版记录中，SM89/SM90 双向编译检查通过，H200 新回归 6 项和既有转换子集 48 项通过。数值样本限制为共同范围的有限编码，覆盖 signed zero、次正规数和舍入边界；没有声称覆盖溢出及 NaN 策略。

## 4. Review：数值正确与语言契约是两件事

维护者不接受隐式 upcast/downcast。返修移除了自动中转，并验证三类行为：

| 输入操作 | 返修后的预期 |
|---|---|
| 直接 E4M3 → E5M2 或反向 | 清晰的前端错误，不进入底层断言 |
| 用户显式 FP8 → FP16 → 另一 FP8 | 保持可用并与独立参考比对 |
| 同格式 identity cast | 保持全部编码 |

这一步不是继续扩展支持范围，而是明确当前能力边界。错误检查不能仅接受“任意非零退出”，否则内部崩溃也可能被误当作正确拒绝。

## 5. 返修验证

| 验证 | 结果 | 能证明什么 |
|---|---|---|
| 已发布旧补丁的编译对照 | 4/4 直接转换可编译 | 确认被移除的隐式行为原先存在 |
| SM89/SM90 编译矩阵 | 12/12 通过 | 4 个前端拒绝、4 个显式链成功、4 个 identity 成功 |
| H200 新回归 | 14 通过 | 含双向拒绝、6 个显式链数值检查、2 个 identity 检查 |
| 既有浮点转换子集 | 48 通过，110 未选入 | 已选范围没有发现回归 |
| 定向代码检查 | 12 通过，6 不适用 | 适用静态检查完成 |

数值链与 Torch 参考按字节比较；identity 覆盖全部 256 编码。SM89 没有物理运行验证，也未覆盖 AMD、解释器或完整项目 CI。

## 6. 发布与边界

10 月 15 日以普通新提交更新原 PR、正文及 issue 说明，并请求维护者复审；原记录仍为等待复审，不代表已批准或已合入。本次归档未查询最新状态。

本例的经验是先拆开 frontend 策略、lowering 能力和数值语义三个层次。可运行的替代实现仍须符合项目对隐式转换的设计要求。
