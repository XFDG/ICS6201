# 跨代 GPU 训练与推理迁移评估

来源：2026-09-21 训练与推理总览；整理日期：2026-10-19。

## 结论

跨代硬件的收益依赖模型结构、输入、精度、运行时和计时层级。受测训练工作负载表现不同：一类计算密集模型有明显吞吐优势，另一类小专家 MoE 没有显示同样优势。推理中，长预填充的趋势也不能直接用于预测解码或 HTTP 服务性能。

原记录将这些结果标为当前迁移栈参考。部分推理严格正确性门禁失败，不能因速度更快或 top-1 一致，就升级成正式硬件加速结论。

## 实验设计

训练侧核对权重和源码清单，覆盖前向、反向和优化器更新，检查 loss/gradient finite，并在预热后统计稳定阶段。低精度扩展采用两端共同支持的 recipe，避免把不同算法配置当作纯设备差异。

推理侧区分 direct forward、模型生成循环和 HTTP streaming 服务，分别记录其计时对象。请求输入、并行策略、精度和软件版本需要与结果一起解释。

| 检查 | 可支持的结论 | 不足以支持的结论 |
|---|---|---|
| 权重与源码内容核对 | 控制部分输入和实现差异 | 驱动、扩展、后端二进制完全相同 |
| finite 与短程训练检查 | 受测路径可运行且未出现所查异常 | 长期收敛与质量等价 |
| logits 数值门禁 | 该输入下满足预设误差要求 | 仅凭 top-1 相同就视作通过 |
| direct forward 计时 | 该层级的执行速度 | HTTP TTFT、TPOT 或系统吞吐 |
| 同模型配对结果 | 相同口径下的迁移趋势 | 不同模型绝对吞吐的统一排名 |

## 失败与结果分级

部分推理路径出现 logits 误差超限或执行异常，正式验证链路因此未完成。单独保留的速度扫描只能用于定位后续迁移工作。加载失败、没有成功请求或一端显存不足的配置应明确留空，不能用残余样本计算加速比。

另有 direct 与 service 趋势相反的观测，说明框架调度、Attention 后端和软件栈足以影响最终收益。继续评估应先确定实际部署层级，再选择相应指标。

## 后续工作

优先修复数值门禁和运行失败，再缩小两端软件差异；训练与服务分别建立稳定可重复的测试合同。推理 MFU 尚缺统一的有效计算量与峰值分母定义，不补造数值，也不直接套用训练 MFU。

公开版不包含专有模型名称、参数组合、checkpoint、原始 token、绝对吞吐、功耗和部署拓扑。上述定性结论来自历史报告，本次未追加硬件测试。
